Private Transactions

Shield balances and transfers from public view using zero-knowledge proofs. Transactions execute on-chain without exposing senders, receivers, or amounts - while preserving full auditability for authorized compliance reviewers.

Groth16 / zk-SNARK BabyJubJub ECC Poseidon Hash EVM + Solana UTXO Model

Cryptographic Primitives #

The OMS privacy module is built on three cryptographic components, each chosen for compatibility with on-chain verification at low cost.

BabyJubJub Elliptic Curve

A twisted Edwards curve operating over the BN254 prime field. Natively compatible with EVM zk-SNARK circuits, making elliptic-curve operations inside a proof cheap enough for production use.

ax² + y² = 1 + dx²y²
// Field prime p = 21888242871839275...617 (BN254 Fr)
// a = 168700, d = 168696

Poseidon Hash Function

A zk-SNARK-native hash function. Unlike SHA-256, Poseidon operates directly over prime fields - no bit operations, dramatically fewer R1CS constraints. Used throughout for commitments, nullifiers, and Merkle tree nodes.

Groth16 zk-SNARK

All privacy circuit proofs use Groth16 over BN254. Constant-size proofs, fast on-chain verification. Circuits are compiled to R1CS using Circom 2.x with circomlib primitives.

ℹ
Trusted Setup: Phase 1 (universal Powers of Tau) reuses Polygon Hermez's ceremony - no re-run required when circuits change. Phase 2 is circuit-specific; any circuit update triggers a new Phase 2 only. The on-chain verifier uses the fixed verifying key.

Key Derivation #

Each OMS private account derives two independent keys from a single Ethereum wallet signature. The signature acts as deterministic entropy - no new secrets need to be stored.

Spending Key

  • Authorizes UTXO spends
  • Derived via ECDSA signature on secp256k1
  • Deterministic - same wallet, same key
  • Never leaves the client
  • Separate from the EOA private key

Viewing Key

  • Decrypts incoming commitments
  • Derived from spending key via libsodium crypto_box_seed_keypair
  • Curve25519-based keypair
  • Read-only - cannot authorize spends
  • Delegatable to org accounts
Derivation Flow 
// 1. User signs a deterministic message with their ETH wallet
const sig = await wallet.signMessage("oms_private_account_v1")

// 2. sig.r || sig.s used as 32-byte seed → Spending Key
const spendingKey = deriveSpendingKey(sig)   // BabyJubJub scalar

// 3. Spending Key seeds Curve25519 keypair → Viewing Key pair
const { privateKey: vkPriv, publicKey: vkPub } =
  libsodium.crypto_box_seed_keypair(spendingKey)

Stealth Addresses #

Every transfer generates a fresh one-time address for the recipient. On-chain observers cannot link two transactions to the same user, nor identify the recipient of any transfer.

Construction

A user's canonical public key C is a BabyJubJub point derived from their spending key vk and the curve generator G:

C = vk · G

// A stealth address is a pair (H0, H1) satisfying:
vk · H0 = H1

// Generated by the sender using random scalar z:
H0 = z · C, H1 = z · G

// Stealth address commitment (on-chain identifier):
StealthAddress = Poseidon4(H0x, H0y, H1x, H1y)
◆
Per Fauzi et al., it is computationally infeasible to link two stealth addresses to the same private key, or to extract the private key from a stealth address. Each transfer uses an independently randomized address.

User flow

1
Connect wallet

Sign once to derive your OMS private account credentials. The signature deterministically recreates spending and viewing keys - nothing new is stored.

2
Receive to private balance

Sender computes a stealth address for the recipient and creates a UTXO. Only the commitment hash appears on-chain.

3
Spend or transfer privately

Wallet generates a ZK proof attesting ownership and value conservation - without revealing which UTXOs were consumed.

4
Public EOA stays unlinked

Only commitments, nullifiers, and Merkle roots are visible on-chain. The EOA address is never associated with private inflows or outflows.

UTXOs, Commitments & Nullifiers #

Private balances use a UTXO model. Each unit of value is a discrete note; spending it produces a nullifier that permanently prevents reuse.

UTXO Structure

Field Type Description
tokenAddress address ERC-20 contract address. Zero address = native ETH.
amount uint256 Token quantity held by this note.
stealthAddress field BabyJubJub stealth address owning this UTXO.
timestamp uint64 Creation time, baked into the commitment hash.
tokenId uint256? Optional NFT identifier.

Commitment

Commitment = Poseidon4(tokenAddress, amount, stealthAddress, timestamp)
// Zero-amount UTXOs produce a zero commitment (padding slots)

Nullifier

Signature = Poseidon2(spendingKey, Commitment)
Nullifier = Poseidon2(Signature, Commitment)
// Recorded on-chain after spend - prevents double-spend

On-chain vs. off-chain UTXO creation

Off-chain (default)

  • Full UTXO computed client-side
  • Only commitment hash stored on-chain
  • Encrypted output lets recipient reconstruct
  • Best for transfers with known amounts
  • Maximum privacy

On-chain

  • Smart contract constructs UTXO during execution
  • Required when final amounts are unknown pre-execution
  • DEX swaps, yield accrual, liquidity positions
  • Ownership verified via ECC operations on BabyJubJub

Approved UTXOs

A specialized UTXO type that acts as an on-chain allowance for external protocol interactions (e.g., Uniswap). The inHinkalAddress is contract-specific, preventing cross-protocol linking while enabling proper spend authorization.

inHinkalAddress = Poseidon2(spendingKey, interactionAddress)
// Same user → different inHinkalAddress per contract

Merkle Trees #

All commitments are stored in an on-chain Merkle tree. Spenders prove inclusion of their note against the current tree root - without revealing which leaf they're proving.

Append-only insertions

New leaves are always appended left-to-right. This deterministic ordering prevents ambiguity when multiple parties interact with the tree in parallel, and ensures each leaf index maps unambiguously to insertion order. Only the nodes on the insertion path are recomputed - O(log n) per insert.

Root history window

Because the root changes on every insertion, the contract retains a sliding window of recent roots (e.g., last 100). Proofs generated against slightly older states remain valid within this window. This prevents a denial-of-service vector where a flood of insertions would invalidate honest provers' pending proofs.

Two tree variants

Write-optimized (frontier)

  • Tracks only the right frontier
  • Minimal storage - O(depth) nodes
  • Insertions only - no deletions
  • Default for deposit/transfer flows

Fully mapped

  • Binary-heap indexing - full tree in memory
  • Supports leaf deletion and replacement
  • Higher storage cost
  • Used where commitments can be revoked
ℹ
Hashing rule: Hash(left, right) when both children exist; Hash(left, 0) when only the left child exists. Zero is the placeholder for absent right children - incomplete subtrees still produce deterministic roots.

ZK Circuits #

The core EVM circuit (MainEVMCircuit) is a generalized, multi-token transaction circuit. A single proof covers up to inputCount input UTXOs and outputCount output UTXOs across tokenCount distinct tokens.

Template parameters

Circom
MainEVMCircuit(tokenCount, inputCount, outputCount, treeDepth)

// Instantiated at fixed sizes for concrete proving artifacts:
// 1×2×1  - single token, 2 inputs, 1 output
// 2×2×2  - dual token, 2 inputs, 2 outputs
// 3×2×1  - triple token, 2 inputs, 1 output
// Min0   - minimum-size (padding-only proof)

Circuit gadgets

StealthAddressCalculatorExtended Derives per-input note public key - supports legacy and new derivation schemes in one proof
CommitmentCalculator Poseidon-4 commitment from UTXO fields; zeroed for zero-amount inputs
Signature Poseidon-2 signature of a commitment under the nullifying key
NullifierCalculator Poseidon-2 nullifier from commitment + signature; zeroed for zero commitments

MerkleRootCalculator Recomputes Merkle root from leaf + sibling path
OverflowPreventer Range-checks all amounts to prevent field wrap-around

Enforced Constraints #

The circuit enforces nine conditions. Every proof that passes on-chain verification satisfies all of them simultaneously.

  1. 1 Valid spending signature
    EdDSA-Poseidon verifies that eddsaSignature is a valid signature on signedMessageHash under spendingPublicKey. Proves the prover controls the spending key without revealing it.
  2. 2 Message pinning
    message = Poseidon1(messageSeed). The public message is forced to be the Poseidon hash of a private seed known only to the prover.
  3. 3 Correct nullifiers
    For each input, the circuit reconstructs the note's public key, recomputes the commitment and nullifier, and asserts equality with the publicly declared nullifier. Prevents double-spending.
  4. 4 Valid Merkle membership
    MerkleRootCalculator folds each input commitment up through its sibling path and asserts the resulting root equals rootHashHinkal. Skipped for zero-amount padding inputs.
  5. 5 Correct output commitments
    CommitmentCalculator recomputes each output commitment and asserts equality with the declared outCommitments.
  6. 6 Balanced amounts
    Per token type: inTotal + amountChanges = outTotal. No value is created or destroyed inside the proof.
  7. 7 Distinct token addresses
    All entries in erc20TokenAddresses must be unique. Enforced via O(T²/2) comparators.
  8. 8 Sender stealth address derivation
    StealthAddressCalculator derives the sender's stealth address and exposes outStealthAddress and outH1Ay for cheap on-chain commitment reconstruction.
  9. 9 Overflow prevention
    All input and output amounts are range-checked via OverflowPreventer to prevent field wrap-around.
